0.  HOW TO READ THIS PLAN
═════════════════════════════════════════════════════════════════════════════

  TASK ID SCHEME
    T<phase>.<workstream>.<seq>       e.g. T1.ING.03
    Workstream codes match the PRD module codes:
      ING GRF TPP CLS ATT CNF EVD SHY CAS UIX ADM OBS MLP PLT(platform)

  EFFORT UNITS
    Effort is expressed in ENGINEER-DAYS (ED) for a competent engineer
    already familiar with the stack. These are planning estimates for
    sequencing and dependency reasoning, not commitments. They are
    deliberately not converted into calendar dates, because calendar dates
    for a team whose size is not yet fixed would be fiction.

  PRIORITY
    P0 required for the SIH prototype demo
    P1 required for a credible pilot
    P2 production hardening
    P3 post-v1

  PHASE GATE
    A phase does not close because its tasks are done. It closes when its
    EXIT CRITERIA pass, verified by the named verification method. A task
    list is a plan; an exit criterion is a fact.

1.  DELIVERY STRATEGY & PHASE MAP
═════════════════════════════════════════════════════════════════════════════

1.1  THE STRATEGY IN ONE PARAGRAPH

  Build the evidentiary spine first and the intelligence on top of it. Most
  teams building this product would start with the GNN because it is the
  interesting part. That ordering produces a clever classifier with nowhere
  trustworthy to put its output. PHANTASM instead builds ingestion,
  cross-validation, canonical storage and the chain-adapter abstraction
  first, so that every model output from Phase 2 onward lands in a store
  that already knows its provenance, its finality status, and its version.

1.2  PHASE MAP

  ┌───────┬──────────────────────┬──────────────────────────────────────────┐
  │ Phase │ Name                 │ The question it answers                  │
  ├───────┼──────────────────────┼──────────────────────────────────────────┤
  │  1    │ Foundation           │ Can we get trustworthy multi-chain data   │
  │       │                      │ into a canonical, provenance-aware store? │
  │  2    │ Intelligence Core    │ Can we tell what an unlabelled wallet is, │
  │       │                      │ and separate laundering noise from money? │
  │  3    │ Attribution Engine   │ Can we find the nearest custodial hop and │
  │       │                      │ say honestly how sure we are?             │
  │  4    │ Evidence & Legal     │ Can a court verify it and can an officer  │
  │       │                      │ act on it lawfully?                       │
  │  5    │ Hardening & Scale    │ Can it be deployed, defended and operated │
  │       │                      │ by an agency?                             │
  └───────┴──────────────────────┴──────────────────────────────────────────┘

1.3  DEPENDENCY GRAPH BETWEEN PHASES

    Phase 1 ─────────────▶ Phase 2 ─────────────▶ Phase 3
       │                      │                      │
       │                      └──────────┬───────────┘
       │                                 ▼
       └──────────────────────────▶  Phase 4  ──────▶ Phase 5

  Phase 4 depends on Phase 1 (canonical facts, finality, provenance) and on
  Phase 3 (a scored path to seal), but NOT on Phase 2's model quality — the
  evidence pipeline is model-agnostic by design. This is deliberate: it means
  Phase 4 can be built in parallel with Phase 2 by a second engineer, and it
  means a model regression never breaks the evidentiary machinery.

1.4  PARALLELISATION OPPORTUNITIES

  ┌──────────────────────────────┬───────────────────────────────────────────┐
  │ Can run in parallel          │ Why it is safe                            │
  ├──────────────────────────────┼───────────────────────────────────────────┤
  │ P1 ingestion ∥ P1 UI shell   │ Contract-first: the API schema is agreed  │
  │                              │ before either side is built.              │
  │ P2 models ∥ P4 evidence      │ Evidence pipeline is model-agnostic.      │
  │ P3 search ∥ P4 dossier tmpl. │ Template needs the schema, not the result.│
  │ P5 security ∥ everything     │ Threat modelling starts in Phase 1.       │

      React/Next.js shell, graph canvas, confidence components, all screens.
  R5  EVIDENCE / SECURITY ENGINEER
      Merkle proofs, verifier utility, audit hash chain, RBAC, signing,
      dossier generation.
  R6  DOMAIN / LEGAL-TECHNICAL LEAD
      Statutory templates, VASP registry curation, SAHYOG payload contract,
      demo narrative, honesty review of every user-facing claim.

  R6. Without someone who owns the legal correctness of the output and the
  honesty of the claims, the team builds an impressive graph tool that
  cannot be used and cannot be defended. On this project R6 has veto power
  over any user-facing statement — including the pitch deck.

4.  ENGINEERING STANDARDS APPLIED FROM DAY ONE
═════════════════════════════════════════════════════════════════════════════

  These are not Phase 5 activities. Retrofitting any of them costs more than
  doing them from the first commit.

  ES-01  Money is NUMERIC(78,0) base units. A CI lint rejects FLOAT/REAL/
         DOUBLE columns matching /(value|amount|balance|fee)/.
  ES-02  Every externally-sourced record carries ingest_run_id, provider,
         fetched_at, and a digest. No exceptions, from the first ingestion
         commit.
  ES-03  Every API endpoint declares its required permission. A missing
         declaration fails the build.
  ES-04  Secrets never in code, images, or committed env files. Secret
         scanning blocks merges from day one.
  ES-05  Structured logging with a correlation id propagated across every
         service hop, from the first service.
  ES-06  Migrations are forward-only and reviewed; any migration touching an
         evidence-bearing table needs a second reviewer.
  ES-07  Model artefacts are hash-addressed and immutable from the first
         trained model, not from the first promoted one.
  ES-08  Test coverage floor: 80% on evidence/proof/legal modules, 60%
         elsewhere. Evidence code is the highest-risk code in the product.
  ES-09  Determinism: every stochastic component takes an explicit seed
         parameter from its first line of code. Adding seeding later means
         auditing every call site.
  ES-10  Contract-first API design: the OpenAPI schema is agreed before the
         frontend and backend diverge.

  ─────────────────────────────────────────────────────────────────────────
   E1.1  A real Bitcoin address and a real Ethereum address both ingest
         end-to-end and appear in both stores.
         VERIFY: automated integration test against live providers.
   E1.2  Ingesting the same address twice creates zero duplicate transfers
         or edges.
         VERIFY: replay test asserting row and relationship counts.
   E1.3  A transaction with disagreeing providers is marked CONFLICTED and
         its field-level diff is retrievable.
         VERIFY: test with a stubbed disagreeing provider.
   E1.4  A transaction below the chain's confirmation minimum is marked
         PENDING_FINALITY and is invisible to path search.
         VERIFY: unit + integration test.
   E1.5  A case cannot leave DRAFT without an authority reference, tested by
         attempting the update directly in SQL.
         VERIFY: the DB CHECK constraint rejects it.
   E1.6  Tampering with an audit row is rejected, and altering one via a
         superuser breaks the chain and is detected by the verifier.
         VERIFY: negative test invoking fn_verify_audit_chain.
   E1.7  No FLOAT column holds a monetary value anywhere in the schema.
         VERIFY: the ES-01 CI lint passes.
   E1.8  Adding a third chain requires no change to any core service module.
         VERIFY: architecture fitness test asserting no chain-specific
         imports outside the adapters package.

  PHASE 1 RISKS
   - Provider rate limits throttle development. Mitigate: aggressive local
     caching of immutable facts from day one; a fixture corpus for tests so
     CI never hits a live provider.
   - Tron/Solana semantics differ more than expected. Mitigate: they are P1,
     scheduled after the interface has been proven by two dissimilar chains.

6.  PHASE 2 — INTELLIGENCE CORE
═════════════════════════════════════════════════════════════════════════════

  OBJECTIVE
    Determine what an unlabelled wallet is, and separate obfuscation noise
    from meaningful value flow — both with measured, honestly-reported
    accuracy.

─────────────────────────────────────────────────────────────────────────────
  WORKSTREAM MLP — ML PLATFORM (built before the models, deliberately)
─────────────────────────────────────────────────────────────────────────────
  T2.MLP.01  P0  2 ED   Model registry tables + artefact store; hash-
                        addressed immutable artefacts.
  T2.MLP.02  P0  3 ED   Evaluation harness enforcing TEMPORAL splits, with
                        minority-class metrics, PR-AUC, bootstrap CIs,
                        stratification by activity decile, and an ablation
                        runner.
  T2.MLP.03  P0  1 ED   Model card template with mandatory failure-modes and
                        prohibited-uses sections; promotion blocked without.
  T2.MLP.04  P1  2 ED   Shadow-mode serving and comparison recording.
  T2.MLP.05  P1  1 ED   Drift monitoring: abstention rate, mean max
                        probability, feature PSI, override rate.

  NOTE ON ORDERING: the evaluation harness precedes the first model. A team
  that trains first and evaluates later invariably discovers it used a random
  split, and by then the impressive number is already in the deck.

─────────────────────────────────────────────────────────────────────────────

  T2.TPP.03  P0  3 ED   Pattern classifier: ORGANIC / PEEL_CHAIN / SMURFING

  T2.TPP.04  P0  2 ED   Soft pruning with prune_reason; "show pruned" path
                        preserved; per-asset dust thresholds.
  T2.TPP.05  P1  4 ED   Neural Hawkes variant behind a config switch, with
                        comparative metrics recorded against the MLE fit.
  T2.TPP.06  P1  2 ED   Burst extraction and the intensity chart data
                        endpoint for the node inspector.

─────────────────────────────────────────────────────────────────────────────
  WORKSTREAM CLS — CLASSIFICATION
─────────────────────────────────────────────────────────────────────────────
  T2.CLS.01  P0  3 ED   Feature engineering: structural (degree, fan-in/out
                        ratios, clustering), temporal (from TPP), value
                        (distribution, round-number rate), and contract
                        features. Versioned feature spec.
  T2.CLS.02  P0  2 ED   Heterogeneous subgraph extraction (Cypher Q7) into
                        PyG hetero batches, preserving node and edge types.
  T2.CLS.03  P0  5 ED   HGT node classifier: training loop, temporal split,

  T2.CLS.04  P0  3 ED   R-GCN relational encoder; joint-vs-separate decision

  T2.CLS.05  P0  3 ED   Elliptic dataset pipeline + baseline reproduction

                        comparison points, with protocol differences stated).
  T2.CLS.06  P0  2 ED   Probability calibration (isotonic / temperature) as

  T2.CLS.07  P0  2 ED   Abstention threshold → UNKNOWN, rather than forcing
                        an argmax label.
  T2.CLS.08  P0  2 ED   Contract bytecode/selector signature index and

                        structurally separate from the model score.
  T2.CLS.09  P1  4 ED   TGN dynamic memory for sparse and zero-day wallets.
  T2.CLS.10  P1  2 ED   Human override flow with justification, versioned

  T2.CLS.11  P1  2 ED   Explainability capture: top features and
                        per-relation attention mass, faithful to the actual
                        computation.

  ─────────────────────────────────────────────────────────────────────────
  PHASE 2 DELIVERABLES
  ─────────────────────────────────────────────────────────────────────────
   D2.1  Model registry with immutable artefacts and mandatory model cards.
   D2.2  Evaluation harness that makes a random split structurally
         impossible.
   D2.3  Hawkes temporal profiling with pattern classification and soft
         pruning.
   D2.4  HGT + R-GCN classifier with calibrated probabilities and an
         abstention class.
   D2.5  Measured Elliptic results with ablation table, stratified metrics,
         bootstrap intervals, and a written negative-findings section.
   D2.6  Contract signature index.

  ─────────────────────────────────────────────────────────────────────────
  PHASE 2 EXIT CRITERIA
  ─────────────────────────────────────────────────────────────────────────
   E2.1  Every reported metric comes from a temporal split. VERIFY: the
         DB CHECK on split_strategy plus a harness assertion.
   E2.2  The ablation table exists and includes a well-tuned gradient-
         boosting baseline on engineered features. VERIFY: the table is
         published in the model card, including any case where the simple
         baseline wins.
   E2.3  Calibration is measured (ECE, Brier) and a reliability curve is
         retrievable via the API. VERIFY: endpoint test.
   E2.4  Metrics are reported stratified by wallet activity decile, showing
         the sparse-wallet degradation explicitly. VERIFY: model card review.
   E2.5  A known peel-chain sequence is detected and flagged. VERIFY: test
         against a labelled historical example.
   E2.6  Pruning is non-destructive: pruned edges remain retrievable.
         VERIFY: integration test.
   E2.7  A model cannot be promoted without a card containing failure modes
         and prohibited uses. VERIFY: the DB CHECK rejects the promotion.
   E2.8  Negative findings are documented. VERIFY: R6 review sign-off.

  PHASE 2 RISKS
   - Elliptic is Bitcoin-only and its label taxonomy does not match the
     PHANTASM class set. Mitigate: state the mapping explicitly in the model
     card; do not silently reinterpret licit/illicit as a service taxonomy.
   - Overfitting to a benchmark that does not represent Indian typologies.
     Mitigate: this is disclosed, not solved. DR-002 requires saying so.
   - GPU availability. Mitigate: CPU inference path maintained and tested;
     training is the only GPU-dependent step.

    a defence expert's replay demand, and that failure surfaces in a
    courtroom rather than in CI.

      requires a configured production endpoint to exist.
    - The MOCK chip renders from server-supplied state, never from a client
      flag, so it cannot be suppressed from the browser.
    - No environment other than PILOT may hold real case data. Enforced by
      configuration and by the deployment runbook.

  RELEASE
    - Trunk-based with short-lived branches; CODEOWNERS requiring a second
      reviewer on evidence, legal and migration paths.
    - Expand → backfill → contract for schema changes, with contract deferred
      to a later release than expand.
    - Model promotion is a separate, audited workflow from code deployment.
      A model going live is not a deploy.

17.  POST-PILOT ROADMAP (beyond v1)
═════════════════════════════════════════════════════════════════════════════

  Sequenced by value, not by novelty.

  R1  Production fine-tuning on FIU-IND-labelled case data, with the
      curator-gated label pipeline already built in Phase 2.
  R2  Confirmed-attribution feedback loop: every VASP response confirming or
      denying an address becomes a calibration data point. This is the
      highest-value data the system will ever generate about itself.
  R3  Remaining chains and chain families; Layer-2 rollup support.
  R4  Cross-case correlation at national scale with jurisdiction-aware
      visibility, subject to data-sharing agreements.
  R5  Travel-rule data attachment where lawfully available, kept
      structurally separate from on-chain-derived facts.
  R6  External anchoring of the audit chain head, so that even a full
      database compromise cannot rewrite history undetectably.
  R7  Multi-agency deployment model with per-agency key custody.
  R8  Analyst-facing typology authoring: let experienced analysts define
      new laundering patterns as first-class detectable structures rather
      than waiting for a retrain.

  EXPLICITLY NOT ON THE ROADMAP
    Privacy-coin tracing. Person-level risk scoring. Automated freezing.
    Full ownership clustering. Each was rejected for a reason recorded in
    PRD §3.2 and DSF §24; a future team should read those before reopening
    them.
